# Obsidian → Terminal: конвертация кампейн-контента

Конвертация заметок мастера из Obsidian в YAML-пакеты v1 терминала Icarus (Nuxt 3, репозиторий `icarus`). Терминал — это внутриигровый канцелярский терминал Британской Империи, год 2061; читатель — персонаж этого мира, а не игрок за столом.

## Ключевой принцип

Документ пишется голосом внутримирового автора 2061 года — бюрократа, историка или офицера, который живёт в этом мире «сейчас». Он не знает слов «сеттинг», «кампания», «игрок», «мастер», «лор». Он не пишет про текущую эпоху в прошедшем времени: Проект Икар, HMS Peregrine и текущие планы существуют прямо сейчас.

## Голос: настоящее vs прошедшее (главная ловушка)

| Что | Время | Пример |
|---|---|---|
| Историография ДО 2061 (история Империи, давние события) | прошедшее | «Реформы были проведены в 2040-х» |
| Текущая эпоха (Проект Икар, Peregrine, актуальные планы, недавние донесения) | настоящее | «Проект предусматривает отправку…», «гарнизон составит…» |
| Будущее внутри текущей эпохи | «должен/предполагается/состоится» | «Экспедиция должна достичь системы к марту» |

Красный флаг: фразы «проект предусматривал», «судно должно было», «гарнизон насчитывал бы» в документе датированном текущей эпохой — это GM-заметка, пересказанная от прошлого. Перепиши от «сейчас», не меняя факты, числа и имена.

**Факты, числа и имена из заметки мастера не менять никогда.** Меняется только рамка повествования (время/голос) и выкидывается GM-лексика.

## Запрещённая лексика (слова игрока за столом)

Не должно остаться ни одного вхождения: «сеттинг», «кампани», «игрок», «мастер», «лор», «сессия», «сюжет», «NPC». Рационализации и ответы:

| Рационализация | Ответ |
|---|---|
| «Фраза полезна, заменю на нейтральное» | Удалить. Внутримировой автор так не пишет. |
| «Это в скобках, для ясности» | Удалить вместе со скобками. |
| «Один раз — не страшно» | Один раз — уже артефакт. Ноль вхождений. |

Проверка перед сдачей: grep по YAML на каждое слово из списка — 0 совпадений.

## Исключения: что НЕ конвертируется в терминал

- **GM-заметки** — разделы с пометками вроде «GM», «для мастера», «в терминал не публиковать», плюс их содержимое (подготовка сцен, поведение NPC, секреты).
- **Досье персонажей-игроков** — личные дела не публикуются.
- **Служебные заметки мастера** («Развитие Истории», «1. Прилет», Style Guidance).
- **«Почему мир устроен так»** — мета-объяснения для мастера.

Если заметка содержит и мирный документ, и GM-разделы — конвертируется только мирный документ; GM-часть остаётся в Obsidian. Каталог `obsidian/` в репозитории НЕ читается и НЕ импортируется автоматически — работай только с теми выдержками, которые дал владелец.

## Лексикон: только аттестованные термины

Термины в словарь/секцию терминов включаются, только если они встречаются в уже опубликованных документах (проверь grep'ом по `content/*.yml`). Неизвестный термин из GM-заметки («квантовая пена», выдуманное ведомство) — **не публикуется**, а выносится в вопросы владельцу.

## Астрономия: шаг SIMBAD

Для каждой системы, соответствующей реальной звезде:

1. Найди объект в SIMBAD (simbad.u-strasbg.fr) по имени, взять `main_id`, координаты (ra/dec, градусы), параллакс → `distancePc = 1000 / parallax_mas`, спектральный класс, эпоха J2000, `catalogSource: SIMBAD`.
2. Если прямой поиск по имени не находит — искать через таблицу идентификаторов (напр. `SELECT id FROM ident WHERE id LIKE '%Tau%Hydra%'` через TAP/URL-запрос): имя в заметке может отличаться от `main_id`.
3. Реальные координаты — всегда точнее, чем «по оценкам» из заметки. Заменяй оценочные «~10 пк» на вычисленное значение, округлив до 0.01 пк.
4. Если звезда вымышленная или SIMBAD не подтверждает объект — оставь `astronomy: null` и задай вопрос владельцу, не выдумывая координаты.
5. Если реестр уже дал точные координаты, убери из текста оговорки вроде «точные координаты подлежат уточнению» — они противоречат опубликованным данным.

## Формат пакета v1 (точные поля)

Читай `server/domain/import/parse.ts` при сомнениях. Скелет:

```yaml
version: 1
package:
  key: theme-slug          # уникальный, kebab-case
  title: Название пакета
  receivedDate: "2061-02-01"  # строка в кавычках
  source: Адмиралтейство — …
  publicSummary: Одно предложение для журнала пакетов.
categories:
  - key: slug
    name: Название
    parent: parent-slug|null
    order: 0
articles:
  - key: slug
    title: Заголовок
    category: category-slug
    relatedArticles: []    # ключи других статей
    body: |
      ## РАЗДЕЛ

      Текст в Markdown…
systems:
  - key: slug
    name: Тау Гидры
    astronomy:
      designation: MAIN_ID
      raDegrees: 0.0
      decDegrees: 0.0
      distancePc: 0.0
      spectralType: G0V
      catalogSource: SIMBAD
      epoch: J2000
    worldClass: central|middle|outer|uncolonized|unknown
    faction: null
    population: null
    economy: null
    anchors: null
    description: Текст для карты
    article: article-slug|null
routes:
  - key: slug
    from: system-slug
    to: system-slug
    type: main|secondary|experimental|historical
    status: open|closed|dangerous|unknown
    direction: описание
    operator: ведомство
    minimumJumpOrder: null
    description: …
    article: article-slug|null
```

Не добавляй полей сверх схемы (validator их молча игнорирует, но мусор остаётся). Служебные поля — только в `package:`: дата и источник живут там, а не телом статьи.

## Именование файлов и ключи

Файл: `content/YYYY-MM-DD-key.yml` — дата получения префиксом (конвенция репозитория). Ключи пакетов/сущностей — уникальные kebab-case; повторный импорт того же ключа пакета заменяет его целиком (режим replace), поэтому ключи менять нельзя после публикации.

## Проверка и поток публикации

1. Валидация: `npx vitest run content/content.test.ts` — гоняет все `content/*.yml` через реальный импортёр на временной БД. Добавление файла в `content/` требует обновления списка в тесте «discovers the package set».
2. Импорт в живую локальную базу: временный dev-сервер (`ADMIN_USERNAME/PASSWORD` свои, `NUXT_IGNORE_LOCK=1`, порт 3211), логин через `POST /api/admin/session`, затем для каждого файла по порядку `receivedDate`: `POST /api/admin/import/run` (`expectedPackageId: null`) → `POST /api/admin/packages/:id/preview` (должно быть `problems: []`) → `POST /api/admin/packages/:id/publish` (`expectedPackageRevision` из detail). Сервер после — погасить.
3. Публичная видимость зависит от даты кампании: пакет виден, только когда `receivedDate <= currentDate`. Проверка анонимно: `/api/public/archive`, `/api/public/map`, `/api/public/packages`.

## Гейт владельца (обязательно спросить)

Перед публикацией нового пакета собери вопросы и отдай владельцу одним списком:

- Неизвестные/неаттестованные термины и названия (публиковать? переписать? выкинуть?).
- Любые «секретные неопубликованные разработки» из заметки — публиковать ли как доступную персонажам информацию.
- Характеристики, которые в заметке читаются как окончательные, а не целевые.
- Всё, что выглядит мета- («это позже станет важным») — кандидат на исключение.

## Типичные ошибки

- Оставить прошедшее время для текущей эпохи (см. таблицу выше).
- Опубликовать GM-заметку «в комплекте» — исключения жёсткие.
- Придумать координаты вместо SIMBAD-запроса.
- Вставить секцию «Термины» в статью дословно — в терминале термины аттестуются употреблением в тексте, а не словарными списками.
- Забыть кавычки вокруг `receivedDate` (`2061-02-01` без кавычек = YAML-вычитание, сломает парсер).
