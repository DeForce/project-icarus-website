# 0007 — Nuxt Terminal Implementation Plan

> **For agentic workers:** After approval, use `superpowers:executing-plans` or `superpowers:subagent-driven-development`. Implement this plan; do not resume any earlier plan.

Status: Draft for user review. No implementation has started.

**Goal:** Rebuild the ICARUS ship terminal from scratch as one maintainable Nuxt application: shared TypeScript types, Drizzle data access, explicit publication, readable YAML import and practical administrator workflows.

**Architecture:** One Nuxt application (Vue 3 + Vite + Nitro, SSR) with public pages and admin workspace. Domain logic is plain TypeScript modules; Nitro routes are thin HTTP mappings; SQLite is the only datastore. The accepted terminal design and the YAML v1 format are preserved; all previous implementation artifacts are deleted.

**Tech Stack:** Nuxt, Vue 3, TypeScript, Reka UI (headless components), @nuxtjs/i18n (single Russian locale), markdown-it (client-side article rendering, raw HTML disabled), SQLite, better-sqlite3, Drizzle ORM + Drizzle Kit, Zod (server-side only), yaml, Three.js, Vitest, Playwright, Biome, Node.js 24, npm, Docker Compose, Caddy. Self-hosted woff2 fonts; the typeface is chosen later.

**Spec:** `docs/superpowers/specs/0007-2026-11-03-nuxt-terminal-design.md`.

## Global constraints

- Node.js 24 and npm; `package-lock.json` is authoritative. No additional formatter, validator or schema framework beyond the listed stack.
- Keep one public read-only archive, one environment-configured administrator, explicit package publication and the fictional player-login placeholder.
- Campaign default is 2061-01-01; future records stay drafts and are never exposed by changing the date.
- All database access uses Drizzle. Direct better-sqlite3 use is limited to connection setup, pragmas, backup and seed.
- No content cache anywhere: public reads project the published snapshot from SQLite per request.
- No legacy adapters, old-client compatibility, session tables, per-entity revision systems, generic repositories or security infrastructure beyond this plan.
- Code/comments/technical docs/commits are English; player-facing copy stays Russian. Biome choices are authoritative: two spaces, LF, 140 columns, single quotes, semicolons as needed, trailing commas.
- Do not touch Obsidian. Legacy documents 0001/0002/0004/0005/0006 and everything under `website/` are deleted in Milestone 1, before new code lands.
- Each milestone ends in a verified English Conventional Commit; the plan completes only after the final acceptance gate. No push, no branches.
- After acceptance the owner replaces git history with a single clean commit; the implementation must leave no dependency on old history.

## Review focus

1. Two dirty forms save independently; a save never destroys another form's text (Milestone 5).
2. A stale tab writes after metadata edit, cancel or YAML replacement: `expectedPackageRevision` returns 409 and keeps form values (Milestones 2 and 5).
3. A package referencing content newer than its own `receivedDate`, or otherwise broken references: publication fails atomically and drafts stay private (Milestones 2 and 4).
4. Browser history, interrupted requests, no WebGL: page state, cancellation and a readable map fallback remain (Milestones 4 and 6).
5. Missing or WAL-active backup source: backup never creates or migrates a source and restores committed data (Milestone 7).

  app.vue                   # Terminal shell

  components/               # Terminal primitives (panel, dialog, select, remote state)
  pages/
    index.vue               # Home / services
    archive/                # Tree+search, article detail
    map.vue                 # Cartography (client Three.js under the hood)
    packages/               # Journal list and detail
    login.vue               # Fictional unavailable crew login
    admin/                  # Login, dashboard, packages, import
  composables/              # useRemote, usePackageEditor, useAdminRequest

  api/
    public/                 # campaign, archive, articles, map, packages
    admin/                  # session, campaign, packages, changes, import
  middleware/admin-auth.ts  # Guards /api/admin/** except login
  domain/
    content.ts              # Pure projection and snapshot types
    references.ts           # Pure reference/graph checks
    packages.ts             # Draft mutations and publication transactions
    import/parse.ts         # Safe YAML load + Zod validation
    import/plan.ts          # Key/UUID resolution without writes
    import/service.ts       # Preview and transactional import
  database/
    schema.ts               # Six tables, typed JSON payloads
    client.ts               # Connection, pragmas, typed Drizzle instance
    migrate.ts              # Official migrator entry
    seed.ts                 # Explicit demo seed only
    backup.ts               # Read-only-source backup CLI
shared/
  types.ts                  # Payloads, DTOs, enums shared by client and server
  constants.ts              # Limits, enum values
examples/package.yaml       # Documented import example
docs/package-import.md      # Import format documentation
tests/e2e/                  # Playwright scenarios
drizzle/                    # Generated SQL and metadata
scripts/                    # docs:new tooling (kept), db helpers

Helpers stay with their feature until a second real consumer appears. Tests live beside the code (`*.test.ts` for Vitest) or in `tests/e2e/`.

## Milestone 2: Database and publication core

**Files:** `server/database/*`, `server/domain/content.ts`, `server/domain/references.ts`, `server/domain/packages.ts`, `shared/types.ts`, unit tests.

- [ ] Define the six-table schema in `server/database/schema.ts` with typed JSON payloads and inferred row types; Drizzle Kit config; generate and review the initial migration. Boot runs the official `migrate()` against the configured path (`.data/` locally, `db/` in Compose, temp files in tests).
- [ ] Implement pure projection: published changes plus an optional draft overlay produce the snapshot (categories, articles with summaries, systems, routes). Implement pure reference checks: missing references, category cycles, self-routes, entity edited in two drafts.
- [ ] Implement package operations: create/list/detail drafts, metadata update, upsert/cancel change, delete draft — every draft write checks `expectedPackageRevision` and bumps the revision inside one transaction. Implement publication: projection + reference validation against the state visible as of the package's own `receivedDate` + monotonic sequence in one transaction; published packages reject every mutation. Publication has no campaign-date gate — any `receivedDate` is publishable, and public reads filter by the campaign date.
- [ ] Unit tests on temporary databases: fresh 2061 campaign, revision conflict (stale tab after metadata change and after cancel/re-add), publication referencing content newer than the package's own `receivedDate` rejected, future-dated publication allowed and hidden from as-of projections, immutable published package, reference failures atomic.
- [ ] Verify `npm run db:generate -- --name=topic` is a no-op after committing schema/SQL/metadata; commit `feat: implement terminal data model and publication core`.

The demo systems come from a small dev-only script under `scripts/` that queries the SIMBAD TAP service for a named system and writes its coordinates/designation into the import YAML shape; committed results feed the seed, and the application itself never calls external services.
